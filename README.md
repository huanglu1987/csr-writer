# CSR Writer v1.1.0

写向 NMPA/CDE 申报的中文临床试验总结报告初稿。适用于 I 到 III 期。

公司内部工具，仓库里有未公开研究的合成数据和内部写作规范，不要外传。

## 这是个什么东西

说到底它是一个 Python 命令行工具。所有真正干活的代码都在 `csr_writer/` 里，
一共三十多个子命令，从生成骨架、解析 TFL、填数值，一直到合卷出 Word。

外面那几层壳只是为了让不同的 AI 工具能接上：

- `AGENTS.md` 是给 Codex 看的。Codex 打开项目会自动读它，读完就知道该怎么调这些命令。
- `skills/csr-writer/SKILL.md` 是给支持 Skill 机制的平台用的，内容和 AGENTS.md 是一回事。
- `.claude-plugin/` 是早期留下的兼容信息，版本号还停在 0.9.0，现在没什么用。

所以严格讲，它既不是插件也不是 Skill，是一个工具加一份操作说明。
在 Codex 里不需要"安装插件"这一步，把仓库拉下来就行。

## 装

```bash
git clone https://github.com/huanglu1987/csr-writer.git
cd csr-writer
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -e .
```

装完跑一遍回归，确认环境没问题：

```bash
python3 -m unittest discover -s tests
```

应该看到 `Ran 312 tests ... OK`。跑一次大概一分钟。

需要 Python 3.10 以上，依赖只有 python-docx、lxml、PyYAML 三个。
不需要模型 API。LibreOffice 装不装都行，装了才能用排版预检那部分，
没装的话流程照样走完，只是跳过视觉检查。

## 用

### 资料放哪

方案、SAP、TFL 这些真实文件**放在仓库外面**，工具以只读方式读，
用 SHA-256 记住版本。不要拷进仓库——一是这个仓库会被同事共享，
二是版本混了以后追溯就断了。

建议在自己的目录下建一个专门放输入的文件夹，比如：

```
~/csr-inputs/ZYG-XXXX/
    protocol_v3.0.docx
    sap_v2.0.docx
    tfl_shell_20260801.docx
    tfl_results_20260915/        锁库后的结果 TFL
```

### 需要哪些资料

必须有的六样：**方案**（含修订历史）、**SAP**、**冻结的 TFL shell**、
**结果 TFL**、**表图清单的发表编号规则**、**研究基本信息和签字人信息**。

少哪一样会导致什么后果，`docs/输入清单与人工闸门清单.md` 里一项一项写了。
**这份文档在动手之前一定要看完**，它还列了全流程 13 个需要人确认的环节，
每个环节谁负责、不做会卡在哪里。

### 提示词怎么写

在 Codex 里打开这个仓库，然后按阶段说话就行，不用背命令。举几个例子：

刚开始，把资料位置告诉它：

> 我要给 ZYG-XXXX 研究写 CSR 初稿。方案在 ~/csr-inputs/ZYG-XXXX/protocol_v3.0.docx，
> SAP 在同目录 sap_v2.0.docx，TFL shell 是 tfl_shell_20260801.docx。
> 请按 AGENTS.md 的流程开始，先带我把 study_facts 填出来。

study_facts 确认完，做结构和映射：

> study_facts 我确认过了。请生成模块路由和骨架，然后从 TFL shell 建映射提议，
> 按分组给我审阅队列。

锁库拿到结果之后：

> 结果 TFL 在 ~/csr-inputs/ZYG-XXXX/tfl_results_20260915/。
> 请套值并生成 annotated 版本，把所有缺口和待确认列出来给我。

几点经验：

- 一次只推进一个阶段，别让它一口气从方案跑到成稿。中间每一步都有需要人点头的地方。
- 它卡住报错的时候，先看错误码。大部分硬失败是设计成这样的——
  比如 shell 和结果对不上表，它会停下来要你裁决，而不是自己猜。
- 想知道现在能出什么、缺什么，让它出 annotated 版本，缺口都标在里面。

## 出来的是什么

两个 Word 文件：

**annotated 版**把所有缺口、待医学负责人确认的地方、数值来源都标出来，
是给内部审阅用的。

**clean 版**是干净的正文。缺口没关闭完的时候它出不来——这是故意的，
免得半成品被当成定稿递出去。

另外还有一批报告：数值溯源、QC 结果、缺口清单，以及排版预检的缩略图墙
（把整份文档缩成一张图，扫一眼就知道哪页有问题，比在 Word 里翻快得多）。
样子可以看 `examples/reference/视觉检查示例/`。

## 它不做什么

这些是故意划的边界，不是没做完：

不会写 TFL 里没有的数字。找不到就是缺口，它不会推断出一个看着合理的值。

不做个案因果关系判定。研究者在 CRF 里判了什么，它照搬什么，不自己下结论。

不代写申办方的医学综合评价，这个位置永远留给人。

源病历里没有的临床经过它不会编。没有就写"待资料到位后补充"。

不判断资料是不是能递交了。所有检查都过了，也只是说机器这一层没发现问题，
不等于医学、统计、法规同意了。

排版预检用的是 LibreOffice 渲染，和 Word 的分页、字体回退有差别，
只能当粗筛。最后还是要在 Word 里更新域、翻一遍。

## 现在什么状态

v1.1.0，已冻结，312 项回归全绿。

有几件事要心里有数：

**这个工具还没在真实数据上跑过。** 目前所有验证都是在合成项目上做的。
第一次拿真实项目用的时候，建议当成一次正式演练来组织，
让各环节真正的负责人走一遍那 13 道确认，而不是一个人闷头跑完。

方法学章节的守卫有大约 7% 的对抗放行率，放行的都是语法不通的拼接句，
人扫一眼就能看出来，不是那种读着顺但内容是编的。

SAE 叙述走的是最严的路子，只接受事先审过的整句，所以自动化程度最低——
每一例都要有人先把句子写出来确认。这是当初权衡后定的。
