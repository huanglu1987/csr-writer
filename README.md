# CSR Writer v1.1.0

写向 NMPA/CDE 申报的中文临床试验总结报告初稿，适用于 I 到 III 期。

公司内部工具。仓库里有未公开研究的合成数据和内部写作规范，不要外传。

---

## 这是个什么东西

它是一个 Python 命令行工具，干活的代码都在 `csr_writer/` 里。
不是插件，也不是 Skill——那些只是让不同 AI 工具接上的壳。

**你不用记任何命令。** 下面所有事都是打字跟 Codex 说，它替你敲。

---

## 一、装工具（整台电脑只做一次）

工具装一份就够，以后所有研究共用，不用每个项目装一遍。

在 Codex 里随便新建或打开一个会话，把下面这段发给它：

> 请帮我做这几件事，做完告诉我结果：
> 1. 把 https://github.com/huanglu1987/csr-writer.git 克隆到我的用户主目录下，
>    也就是 ~/csr-writer
> 2. 进去建一个 Python 虚拟环境，用 `pip install -e .` 安装
> 3. 运行 `python3 -m unittest discover -s tests`，把测试数量和是否通过告诉我

它应该回你 `Ran 312 tests ... OK`，看到这个就装好了，大概一分钟。
需要 Python 3.10 以上，别的依赖它会自己装，不需要任何模型 API 密钥。

**以后工具有更新**，跟它说一句"把 ~/csr-writer 更新到最新版"就行，
所有项目一起受益。

---

## 二、给每个研究建一个项目文件夹

工具是共用的，但**每个研究单独一个文件夹**，资料和产出都放在自己的文件夹里，
互不干扰，以后归档、应对核查也清楚。

建一个文件夹，名字用研究编号，里面再建两个子文件夹：

```
~/csr-writer/            ← 工具，装一次，所有项目共用

~/CSR-ZYG-XXXX/          ← 这个研究的项目文件夹，在 Codex 里打开这一层
    输入资料/             ← 方案、SAP、TFL 都放这儿
    输出/                ← 生成的报告会放这儿
```

**每次要干活**：在 Codex 里打开这个项目文件夹
（界面上选"打开文件夹"，选到 `CSR-ZYG-XXXX` 这一层），然后直接说话。
工具在哪儿，下面的提示词里会告诉它。

## 三、准备资料

### 先说一件事：文件指纹

后面会反复提到"记录文件的指纹"。指纹就是根据文件内容算出来的一串字符
（术语叫 SHA-256），文件里改一个字，这串字符就完全变了。

工具用它来锁定你给的到底是哪一版方案、哪一版 TFL。因为 CSR 写作周期长，
方案可能改版、TFL 可能重出，光看文件名分不清。这串字符**不用你自己算**，
让 Codex 记就行。

### 文件放哪

统统放进这个研究的 `输入资料/` 里，**不要往 `~/csr-writer` 里放**——
那是所有项目共用的工具，混进项目文件以后就乱了。

`输入资料/` 里可以这样组织，照搬即可：

```
CSR-ZYG-XXXX/
    输出/
    输入资料/
        方案_v3.0.docx                Word 原件，别用 PDF
        方案修订/                      各版修订案，也是 docx
        SAP_v2.0.docx
        TFL定稿_20260915/              统计给的最终结果
            t14-1-1-1.rtf             一张表一个 RTF 最好
            t14-2-2-1-1.rtf
            ...
        方案偏离清单.xlsx
        CRF样表.docx
        伦理与知情同意/
            伦理批件与委员会名单.docx
            知情同意书样本_v2.0.docx
        随机化方案与编号表.xlsx
        研究者与中心名单.docx
        研究基本信息与签字人.docx
```

文件名怎么起随你，Codex 会自己认。**但同一份东西改版之后，
新文件要用新名字**，别用同名覆盖——覆盖了追溯就对不上了。

### 一定要有的

| 资料 | 什么格式 | 找谁要 | 没有会怎样 |
|---|---|---|---|
| 研究方案，含全部修订案 | `.docx` | 临床运营 / 医学 | 研究设计定不下来，骨架出不全 |
| SAP | `.docx` | 统计负责人 | 分析集、统计模型、缺失值处理写不了 |
| 定稿 TFL（表、图、清单） | 一张表一个 `.rtf` 最好；整份 `.docx` 也行 | 统计编程 | 所有数值都是空的，正式版出不来 |
| 方案偏离清单 | `.xlsx` 或 `.docx` | 临床运营 / 数据管理 | 第 10.2 节写不了 |
| 病例报告表样本 | `.docx` 或 `.pdf` | 数据管理 | 附录 16.1.2 缺，这是 E3 必交项 |
| 伦理批件、伦理委员会名单、知情同意书样本 | `.docx` | 法规 / 临床运营 | 第 5 章伦理部分和附录 16.1.3 缺 |
| 研究者与研究中心名单 | `.docx` 或 `.xlsx` | 临床运营 | 附录 16.1.4 缺 |
| 随机化方案与随机号表（随机研究） | `.xlsx` 或 `.docx` | 统计编程 | 附录 16.1.7 缺，这是 E3 必交项 |
| 表图清单的最终编号规则 | 一份清单即可，Codex 帮你转 | 统计编程 / 医学写作 | 正文里"详见表 X"对不上号 |
| 研究基本信息与签字人 | 一份清单即可 | 项目经理 / 法规 | 标题页出不来 |

### 有就更好的

| 资料 | 给了之后 |
|---|---|
| 盲态维护与揭盲记录 | 盲法那节能写成有依据的正文，而不是套话 |
| 试验药品批号与受试者对应表（用了多个批次时）| 附录 16.1.6 能补齐 |
| DMC/IDMC 章程和会议纪要 | 期中分析、数据监查的内容能落位 |
| SAE 和死亡病例经医学审核的结构化信息 | 个例叙述才能生成；没有的话工具不会去编经过 |
| MedDRA、WHODrug 的版本号 | 不良事件和合并用药的编码来源能写清楚 |
| 稽查证书、地区性附件登记 | 附录清单的提交状态更完整 |
| 中心实验室的方法与质控文件 | 附录 16.1.10 能补齐 |
| 参考文献清单 | 第 15 章能自动生成 |
| 关于是否开展 COA 开发的正式说明 | 工具照实转述项目决定。它不选、不验证、不开发量表 |

### 关于格式的几个提醒

**方案和 SAP 一定要 Word 原件，不能给 PDF。** 工具要读表格结构、单元格合并、
修订痕迹，PDF 里这些全没了。只有 PDF 的话得回头要原件；实在只有 PDF，
转出来之后必须有人逐节核对结构对不对——转错了进正文是查不出来的。
（CRF 样表例外，那个只是当附件收，PDF 可以。）

**方案不用先把修订都接受掉再给它。** 工具会把插入、删除、隐藏文字都读出来单独列给你，
那正是要你留意的地方。为了"干净"先接受修订，反而把信息抹掉了。

**TFL 优先用 RTF。** 统计用 SAS 直接导出的 RTF 结构最干净，一张表一个文件。
Word 版也能读，但如果是从 RTF 转过来的，表头层级容易丢。

**Excel、清单类的不用你整理成什么特定格式**，直接把统计或运营给你的原件丢过去，
Codex 会读出来整理好再拿给你确认。

## 四、开始写

医学经理一般是 TFL 定稿之后才开始写报告，下面就按这个情况来。

在 Codex 里打开你的项目文件夹，把这段发给它——
**只需要把研究编号换成你自己的，其余照抄**：

> 我要为 ZYG-XXXX 研究撰写 CSR 初稿，TFL 已经定稿。
> 工具装在 ~/csr-writer，我的资料在当前文件夹的 输入资料/ 下，
> 请把结果写到当前文件夹的 输出/ 里。
>
> 请先读 ~/csr-writer/AGENTS.md 和 ~/csr-writer/docs/输入清单与人工闸门清单.md，
> 然后按下面的方式带我走：
>
> 1. 先把 输入资料/ 里的文件都看一遍，列个清单告诉我：哪些你能用、
>    分别对应报告的哪一部分、还缺什么。缺的东西告诉我该找谁要。
> 2. 记录每个文件的指纹（SHA-256），后面版本变了要能发现。
> 3. 从方案和 SAP 里整理出这个研究的基本情况，用一页纸的中文表格给我核对，
>    不要给我 JSON 或者代码。我确认完你再往下走。
> 4. 之后每做完一个阶段就停下来，把该我确认的东西整理成中文给我看，
>    我说继续你再往下。不要一口气跑到底。
> 5. 任何一步报错或者卡住，把错误码是什么意思讲清楚，告诉我是资料的问题
>    还是需要我做判断，不要自己猜一个答案填进去。
>
> 现在开始第 1 步。

后面就是一问一答了。它每停一次，你看一眼、确认或者纠正，说"继续"。
整个过程大概会停十几次——这些停顿是故意设计的，
每一处都是必须由人负责的判断，跳过去后面也会被卡住。

**中途想看当前进展**，随时可以说：

> 现在能生成的部分先出一版带批注的稿子给我，把所有缺口和待确认的地方标出来。

**全部确认完之后**：

> 我确认的事项都处理完了，请生成正式版，并跑一遍排版检查，
> 把缩略图墙给我看。

## 五、出来的是什么

**带批注版**（annotated）把缺口、待医学负责人确认的地方、
每个数字的来源都标出来，是给内部审阅用的。

**正式版**（clean）是干净正文。缺口没关完它出不来——这是故意的，
免得半成品被当定稿递出去。

另外还有一批报告：数字来源追溯、QC 结果、缺口清单、
方案到 SAP 到 TFL 到 CSR 的双向对照、哪些表图还没被正文引用，
以及排版检查的缩略图墙——把整份文档缩成一张图，红黄绿标出有问题的页，
扫一眼比在 Word 里翻快得多。样子看
[examples/reference/视觉检查示例](examples/reference/视觉检查示例)。

---

## 六、它不做什么

这些是故意划的边界，不是没做完。

不会写 TFL 里没有的数字。找不到就是缺口，不会编一个看着合理的值。

不判断某个不良事件和药物有没有关系。研究者在 CRF 里判了什么就照搬什么。

不代写申办方的医学评价，这个位置永远留给人。

源病历里没有的诊疗经过不会编，没有就写"待资料到位后补充"。

不判断资料是不是能递交了。所有检查都过，也只是说机器这一层没发现问题，
不等于医学、统计、法规同意了。

排版检查用的是 LibreOffice 渲染，和 Word 的分页、字体有差别，只能当粗筛。
最后还是要在 Word 里更新域、自己翻一遍。

## 七、现在什么状态

v1.1.0，已冻结，312 项回归全绿。

**这个工具还没在真实项目上用过**，目前所有验证都是在模拟数据上做的。
第一次拿真实项目用，建议当成一次正式演练来组织，
让各环节真正的负责人都参与，别一个人闷头跑完。

方法学章节的守卫有大约 7% 的漏过率，漏过的都是语法不通的拼接句，
人扫一眼就能看出来，不是那种读着通顺但内容是编的。

个例安全性叙述走的是最严的路子，只接受事先审过的整句，所以自动化程度最低，
每一例都要有人先把句子写出来确认。这是当初权衡后定的。
